# Artifact-to-project pipeline

The command is `letstryrea reconstruct <artifact> --out <new-directory>`.
It applies independently implemented reconstruction recipes to two known
artifacts and capabilities. Generation mode is explicitly `verified-recipe-export`.
Matching keywords, module counts, filenames, or product metadata never enable
a recipe for an arbitrary input.

## Obsidian eligibility

The first recipe, `obsidian-markdown-search-v1`, accepts the exact official
Obsidian 1.14.4 application-update ASAR studied previously:

- Artifact SHA-256:
  `146ef8470d8cbb4a6db209bdc19bf2bad13350444186c0fd93c31087b142b92f`.
- Embedded `app.js`: 3,942,126 bytes, SHA-256
  `958ce57fe22f87fdf121546e46dfccd9c8ee971ce3fd8f801d60d4ece39a2df9`.
- All 12 hashed byte regions in [the source specification](reconstruction-spec.md)
  must match. The source must be an ordinary packed archive entry.

Input hashing streams from an opened regular file. Source inspection allocates
the known embedded JavaScript only after the complete artifact digest matches.
Archive header reading is bounded to 1 MiB; the studied JSON header is about
96 KiB. Linked/unpacked/out-of-bounds source entries are ineligible. Symlink
input paths resolve to the canonical file recorded in the report.

Other versions, modified artifacts, unsupported formats, and malformed archives
produce an unsupported result. A no-recipe outcome is a useful completed
identification step, not a successful reconstruction.

## Stages

1. Reserve a fresh output directory without overwriting anything. Reject
   source/output overlap, including aliases, before creating output parents.
2. Identify the artifact, hash it, and match the exact source evidence.
3. Require REA 6.5.0. Run `inspect-artifact` and verify returned artifact
   identities/integrity results.
4. Run `analyze-javascript-application` on `package.json`, `main.js`,
   `index.html`, `app.js`, and `enhance.js`. Keep the existing 1024 MiB source
   worker heap and 120-second per-source deadline. Preserve command exits/logs.
5. Validate the analysis identity, selected sources, absence of parse/integrity
   failures, and a matching `inspect-analysis-view` summary. Source and semantic
   coverage may remain partial; those limits are retained.
6. Recheck the original artifact and export only the independently authored
   search code, public tests/examples, behavior specification, and curated
   recipe provenance.
7. Run the exported project's actual 28 CLI tests and a representative demo.
   Require a nonzero executed test count, all passed, and no failed, cancelled,
   skipped, or todo checks. Verify the demo's actual search result.
8. Create a deterministic ZIP from an explicit file allowlist. Reject symlinks
   and unexpected files. Save the source manifest, archive checksum, fresh
   verification outcomes, and earlier comparison reference in the job report.

The complete selected-source Evidence can be hundreds of megabytes. It remains
outside the small project ZIP. A compact summary is generated by REA from the
completed Evidence rather than replacing analysis with a superficial check.

## Claims and boundaries

- **Fresh:** the selected artifact probe, REA inspection/application analysis,
  generated source manifest, exported-project tests, functional demo, and ZIP.
- **Historical:** the earlier 69 original-app comparisons. Their record must
  match this artifact and contain successful actual process results. They are
  never described as comparisons rerun by this pipeline.
- **Implemented output:** the supported plain-text Markdown search subset.
  It runs independently using Node.js 24+ and no third-party dependencies.
- **Unimplemented:** arbitrary code synthesis, formats/releases beyond the two recipes,
  full application reconstruction, and a browser upload interface.

The Obsidian artifact is never loaded as executable code. Generated verification runs
our independently written allowlisted implementation and tests. Adding another
recipe requires its own observed behavior, independently authored code,
provenance contract, and meaningful validation; changing only a digest or
keyword list would not establish support.

## Duration recipe

`ms-duration-v1` accepts only the published `ms@2.1.3` npm tarball. See
[the duration specification](duration-spec.md) for the compressed and source
digests, grammar, unit constants, formatting rules, and adapter differences.

The intake checks the compressed digest, bounded TAR structure, and all four
file digests before writing extracted bytes. REA cannot inspect this TGZ through
`inspect-artifact`, so this route performs direct selected-source analysis of
the verified package directory. The report preserves the compressed artifact,
file-manifest, and analyzed-directory identities separately. A directory digest
is never substituted for the incoming tarball digest.

The pipeline exports the independent duration module and CLI, runs their public
test suite and demo, and performs fresh original comparisons before packaging.
The comparator runs the pinned original and exported candidate in different
bounded child processes on a fixed synthetic corpus. It preserves undefined,
negative zero, nonfinite numbers, and exact exceptions in typed outcomes, and
requires every nonzero-count comparison to pass. Source digests must remain
unchanged before and after execution. This recipe deliberately executes the
known MIT reference; unsupported inputs and the Obsidian artifact are not
executed.

Each ZIP uses a recipe-specific fixed file allowlist. The duration ZIP includes
the independent implementation, tests, CLI, specification, provenance, and MIT
notice. Original package files, comparator code, and raw analysis remain outside
the ZIP. A standalone export requires neither REA nor the original package.

## Results

`report.json` includes each stage's outcome, actual child commands/exits,
artifact identity, recipe, partial-coverage statistics, fresh test counts,
historical comparison reference, file manifest, and ZIP checksum. `report.md`
provides the same outcome in readable form. Evidence and command logs live in
`evidence/`.

Exit codes are 0 for a verified export, 1 for a failed run, 2 for invalid input
or an output collision, and 3 for an unsupported artifact. Failed/unsupported
jobs retain diagnostic reports and cannot be presented as successful ZIPs.

Use a new output directory for every attempt. Analysis is fresh in this first
version; unvalidated external evidence caches are not accepted.

## Verified example run

The first full run used the exact Obsidian artifact above. Fresh REA analysis
reported 195 modules with zero parse failures and retained partial coverage.
The exported project's 28 tests and functional demo passed. Its 16,300-byte
ZIP contains 11 allowlisted files. An independent Python ZIP reader verified
its CRCs, extracted the project into a temporary directory, and ran all 28
tests successfully again.

Separate fault-injection runs confirmed that a missing analyzer and conflicting
nested artifact identities produce failed reports with no project or ZIP.
Unsupported-format, output-preservation, alias-overlap, archive-content, and
owned-process timeout cases are covered by the repository test suite.

The [recorded pipeline receipt](verification/pipeline-obsidian-1.14.4.json)
contains the actual stage/command outcomes, source/file/archive digests, fresh
test counts, independent delivery check, fault-injection outcomes, and the
explicit historical-only original-app comparison reference. Complete raw
Evidence remains in the local job directory referenced by that record.

## Verified duration run

The second recipe passed fresh analysis, all 9 exported-project tests, both
CLI demos, and all 1,823 typed original-reference comparisons. The deterministic
ZIP contains 9 files. Independent extraction passed the same 9 tests and all
1,823 comparisons again. All 94 repository checks passed. A deliberately wrong
implementation failed 1,730 comparisons, and a modified TGZ was rejected before
analysis or project creation. The original Obsidian pipeline was rerun through
successful export and all 28 generated-project tests; its original-app
comparisons remain historical.

The [duration verification receipt](verification/duration-ms-2.1.3.json) records
artifact/file/source identities, partial semantic coverage, corpus and candidate
hashes, fresh counts, archive/manifest hashes, delivery checks, and fault checks.
